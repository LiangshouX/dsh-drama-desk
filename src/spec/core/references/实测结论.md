> 每条规则都对应一次实测发现，不是推测。
> 规则正文在 `spec/rules.md`（唯一真源），由 CLI 按阶段筛选后注入给 Agent。

## 1. 参考图数量与身份保持

- **2 张参考图即可稳定保持身份**。SH01 用 wet+dry 两张全身图，SH02 用 wet+face 特写，
  两镜人物都是同一个卷发卡其外套青年，跨镜头可辨认为同一人。
- **道具细节会被精确还原**。SH02 参考图里只是一个小色块的"小菊花贴纸"，
  在生成视频里被还原成清晰的白色雏菊+黄色花心。这是多模态参考最有说服力的证据。
- 结论：**H3 多模态参考模式对"小道具细节"的还原度高于纯文本描述**。
  关键道具必须有参考图，不能只靠 prompt 描述。

## 2. 状态一致性：真正的元凶是「提示词内部矛盾」，不是参考图混合 ⚠️（已归因）

初版结论（SH01 观察）推测"混合互斥状态参考图会互相抵消"。**已被三组归因实验推翻**。

### 归因实验（三组正交对照，各 $0.40）

| 实验 | 参考图 | 提示词 | 生成结果 |
|---|---|---|---|
| T1 | 仅 wet | 全修正（含 `<Picture 1>` 声明、Subject 1 写成湿身） | **湿** ✅ |
| T2 | 仅 wet | 无 `<Picture>` 声明（Subject 1 仍写湿身） | **湿** ✅ |
| T3 | wet + dry | 全修正 + 显式消歧（声明 dry 仅供身份确认） | **湿** ✅ |

三组全部为湿身（人工看首尾帧确认：外套深色湿润有水珠、头发贴额、面部水痕、地面反光积水）。

### 结论

- **C2 提示词内部矛盾 = 唯一真凶**。原 SH01 的 `subject_definitions` 里把 Subject 1 写成
  "wearing a **washed-out light khaki** cotton jacket"（干身描述），
  而 `detailed_description` 里写 "his khaki cotton jacket is **dark and wet**"——
  同一段提示词自相矛盾，模型选了前者。**把 Subject 定义改成湿身后，参考图怎么配都湿。**
- **C3 `<Picture N>` 声明并非必要**。T2 去掉声明同样是湿的。
  → 但**仍建议保留**：声明让模型明确"哪张图定义哪个主体"，对跨镜头角色一致性有利，
  且 T3 证明配合消歧表述可安全混用混合参考。
- **C1 参考图混合并非致命**。T3 同时喂 wet+dry 并显式说明"dry 仅用于确认面部身份、
  不采用其干燥衣物"，结果依然是湿的。**显式消歧有效。**

### 写进 Skill 的规则

1. **同一主体的定义与描述不得互相矛盾**（最重要）。
   凡是 `subject_definitions` 里写了服装/状态，`detailed_description` 必须一致，
   反之亦然。写完自查一遍状态词：wet/dry、day/night、季节能不能对上。
2. **每个参考图声明角色**，用 `<Picture N>` + `retention_analysis` 说明它是
   "外观基准"还是"仅供身份确认"。混合互斥状态时**必须写消歧句**：
   "<Picture 2> shows the same man dry and is used only to confirm his facial identity;
   none of the dry clothing, dry hair, or dry skin of <Picture 2> is applied."
3. **保守做法仍是同一镜头只用同状态的参考图**，消歧句只是补救手段，不是免死金牌。

### 方法论教训（比结论本身更重要）

- **单次观察不能定因**。SH01 只跑了一次就下结论"混合参考图会抵消"，是错的。
  三个可疑因素同时存在时，必须做正交对照。
- 归因成本极低：**3 条 $0.40 的视频 = $1.20**，却锁定了影响所有后续产量的规则。
  比写完代码再返工便宜得多。
- 实验设计原则：**一次只改一个变量**。本次三组分别隔离 C1/C2/C3，
  用 T1 作共同基点做两两对比。

## 3. 口型：voiceover 写法会导致闭唇念台词 ⚠️（关键）

四条提示词（SH01/T1/T2/T3）**全部**包含官方 voiceover 写法：

```
The cellist (S1) says in a calm off-screen voiceover: <d>[Chinese] 雨这么大，还是没人来。</d>
Immediately after the complete <d> block, his lips remain completely closed and his face is turned slightly down toward the cello while the bowing continues.
```

其中 "**his lips remain completely closed**" 是**明确的闭唇指令**，模型照做即无口型。

实测表现：
- SH01：口型不明显（部分遵守）
- T1：口型不太明显
- T2 / T3：**彻底没有口型**（严格遵守指令）

→ **口型问题不是模型能力问题，是提示词写法问题。**

### 规则

- **要口型 → 写画内音**：
  ```
  <Subject 1> (S1) says: <d>[Chinese] 台词。</d> His lips move clearly with the words as he speaks.
  ```
  不要出现 "off-screen voiceover"，不要出现 "lips remain completely closed"。
- **要画外音 → 保留官方写法**，并说明画面中角色嘴唇不动。
- 画内音是 AI 短剧的默认选择；画外音只用于真正的旁白/内心独白。

## 4. 机器验收有盲区，必须人工复核

- `videos_understand` 判定 SH01 相机为 "Static (fixed camera)"，
  **但逐帧对比证明是缓慢推近**（f01 远景 → f03 近景）。
- 本次实验中同一判断再次分歧：T1 判 "Static"，T2/T3 判 "slow push-in"。
  → 同一模型对同类问题的判定**不自洽**，绝不能作为唯一判据。
- 同理，它把人描述为 "teenage boy"（参考图本人确实偏少年相）。
- **规则**：A 组技术参数可自动化判定；**B/C 组语义判定只作参考，不作判废依据**。
  相机运动、年龄、细微情绪等必须人工看首/中/尾三帧。

## 5. 原生音轨能力确认 ✅

- 对白逐字准确：`雨这么大，还是没人来。` — 完全按 prompt 的 `<d>[Chinese]...</d>` 输出。
  **T1/T2/T3 三组全部逐字准确**，对白一致性极高。
- 音轨三要素齐全：对白（人声）+ 环境音（雨声）+ 物理音（弓弦、雨滴）。
- 声景分层可用：`overall_soundscape` 给雨声/弓声，`non_diegetic_music` 给配乐，两者不打架。
- **结论**：H3 原生音轨**可以替代整条 TTS 流水线**。一部 3 分钟短剧省掉 TTS+ASR+对齐三道工序。
- 参考音频（`reference_audios`）本次未测，留待需要精确音色控制时验证。
- **响度实测**（volumedetect）：

  | 镜头 | mean_volume | max_volume |
  |---|---|---|
  | SH01 | -18.6 dB | -0.7 dB |
  | SH02 | -29.3 dB | -18.1 dB |
  | T1 | -14.2 dB | -0.3 dB |
  | T2 | -15.9 dB | -0.5 dB |
  | T3 | -18.7 dB | -1.4 dB |

  → 有对白的镜头 mean_volume 约 -14~-19dB；纯环境音镜头约 -29dB。
  **规则：mean_volume < -45dB 判为无声废片**（留足余量）。

## 6. 小道具会被"搬家" ⚠️

- SH02 中，小菊花贴纸被精确还原在**琴面**上（贴纸本就在琴背板，镜头角度可见）。
- 但 T2 中，模型把一朵白花**放到了背景的路灯柱上**——参考图里琴身的贴纸，
  在 T2 里跑到了错误位置（T2 只喂了 wet 单图，贴纸在 wet 参考图里是背板角度，不易辨识）。
- **规则**：
  - 关键道具的贴纸/标志若在参考图中位置偏远或角度不利，模型可能重新安置它。
  - **道具特写镜头要单独准备一张该道具的清晰参考图**，不能只靠人物全身图。
  - 这正是 SH02 用了 wet+face 两图（face 特写让贴纸更清晰）而效果更好的原因。

## 7. 相机运动词汇有效

- prompt 写 "The camera performs a slow Push In with small amplitude" → 实测确实缓慢推近。
- 官方词汇表（Push In/Pull Out/Pan/Truck/Tilt/Arc/Tracking/Static）**直接用，不要自造同义词**。

## 8. 实际耗时与成本（重要：比文档快得多）

| 指标 | 实测值 | 文档/预期 |
|---|---|---|
| SH01 / SH02 生成耗时 | 约 1.8 分钟 | 文档称 H3 需 15–30 分钟 |
| T1 / T2 / T3 生成耗时 | T2 约 1.5 分，T1 约 1.8 分，T3 约 2.2 分 | 同上 |
| 单条成本（768P 5s） | $0.40 | 一致 |
| 5 镜累计 | $2.00 | — |

- **H3 实际远快于文档宣称的 15–30 分钟**。这意味着：
  - 单会话跑完 10-15 个镜头是可行的，不必设计成"提交完就结束会话"
  - 但**仍不能一次提交 30 个**——并发与排队会拉长总时长，且中途失败难以归因
  - CLI 的批量提交仍需要，但可以改成"一次提交 N 个 + 一个轮询器管全部"
- **单轮询器管理多任务已验证可行** ✅：本次用一个轮询器同时管 T1/T2/T3，
  每 30 秒轮询一遍全部任务，全部终态后统一退出。
  相比三个独立轮询器（上一轮做法），资源占用更少、状态更集中。
  → **CLI 批处理设计：一次提交 N 个 + 一个轮询器管全部 + 统一下载验收。**
- 成本侧：30 个 5s 镜头 768P ≈ $12，按量付费完全可承受；Build 档周额度应能覆盖大部分。

## 10. 落地教训（工程层面）

- PowerShell 下 `//` 不是合法 Python 注释 → 用 `#`。
- `subprocess` 调 `mcode-tools`（.cmd 包装器）必须 `shell=True`，否则 WinError 2。
- PowerShell 5.1 里 `ConvertTo-Json` + `Set-Content` 会带 BOM，且多行字符串转义易坏
  → **参数文件一律用 Python `json.dump` 生成**，不要用 PowerShell 拼 JSON。
- 控制台中文显示为 GBK 乱码是显示问题，文件本身 UTF-8 正常，不要因此误判。
- `mcode-tools` 的 node 警告（UNDICI-EHPA）走 stderr，**不要**用 `$ErrorActionPreference='Stop'`，
  否则警告被当成致命错误。保持 `Continue`。
- bash 工具对工作区内的递归写入/删除有安全策略拦截：
  `Copy-Item`/`New-Item -Force` 常被误判。**改用 `write` 工具落盘**，
  删除用顶层 `rm -- <目标>`（走可恢复删除，进回收站）。
- **台账必须防并发写**（2026-11-01 实测踩坑，已修 drama.py）：
  1. `cmd_poll` 长时间持有整份 ledger 快照再整体写回 →
     另一个轮询器或提交脚本期间写入的条目会被**静默覆盖丢失**
     （实测丢了 P6 的 task_id，正好是幂等最怕丢的东西）。
     修法：写回前重新读盘，按 shot_id 合并。
  2. `os.replace` 在 Windows 上遇到文件占用会抛 WinError 32 → 加退避重试。
  3. `totals.cost_usd` 原本是「每记录一次 succeeded 就累加」，
     同一条被记录两次就重复计费，**预算守卫会低估花费**。
     修法：改成每次从 entries **重算**（幂等、可自愈）。
- **`drama.py` 没有 `asset remove` / `asset prune`**：
  文件重命名后会在 assets.json 留下指向不存在路径的孤儿条目，本轮用临时脚本清理。
  这是 CLI 的待补项。
- 频谱图 `showspectrumpic` 用 `atrim` 截取时要确认语音真正落在窗口内，
  否则会截到静音段并得出错误结论（本轮踩过一次）。

## 11. 音色控制：7 探针实测（2026-11-01，$3.36）⚠️ 关键

> 完整报告见 `docs/音色验证实验报告.md`，方法论见 `docs/音色控制验证方法.md`。
> 工作区 `workspaces/voice-probe-20261101/`。

### 11.1 先破除一个假象

原始 5 条里 4 条被听成"音色统一"。ASR 复核后真相：4 条**说的是同一句话**、
speaker 行逐字相同、**全部没有音色描述词**。统一被"提示词相同"完全解释掉了。

### 11.2 F0 在有伴奏的音轨上测的是乐器 ⚠️

无台词的 SH02 被自相关测出 **197 Hz / 204 个有声帧** —— 那是大提琴旋律。
干净 TTS 样本的 F0 只有 114–190 Hz。

> **测音色必须在无乐器、无配乐的场景下测。**

### 11.3 零假设对照（最容易被漏掉的一步）

P2 提示词**逐字重发**得到 P6 → 两者差异 = **3.72 dB / 0.45 半音**。
这是所有"差异"的尺子。没有它就无法区分变量效应与生成随机性。

### 11.4 结果矩阵（以 P2 为基准，shape = 电平归一化 LTAS 距离）

| 变量 | shape | /零假设 | F0 半音差 | 判定 |
|---|---|---|---|---|
| 换台词 | 8.86 dB | 2.4× | −10.6 | 显著改变 |
| **加音色描述词** | 8.14 dB | 2.2× | **−11.5** | **显著改变，效应最强** |
| 换场景 | 7.33 dB | 2.0× | −9.5 | 显著改变 |
| 加 `reference_audios` | 6.02 dB | 1.6× | −1.35 | 轻微，远小于参考音频的 6.8 半音 |

### 11.5 `reference_audios` 实测不能钉死音色 ⚠️

| 探针 | 接法 | 参考音频 F0 | 实际输出 F0 | 与默认差 | 与参考差 |
|---|---|---|---|---|---|
| P5 | 参考说台词①，角色说台词② | 190.4 Hz | 139.1 Hz | −1.35 半音 | −5.44 半音 |
| **P7** | 参考说台词②（内容对齐），`pitch=+6` | **200.9 Hz** | **129.5 Hz** | **−0.12 半音** | **−6.67 半音** |

零假设（P2↔P6，同提示词重发）的音高差是 **0.45 半音**。
P7 的输出与 H3 默认音色差 **0.12 半音**（比零假设还小），与参考音频差 6.67 半音。

频谱图目视确认：P2 / P6 / P5 / P7 的谐波间距完全一致，参考样本明显更密。

- **结论：不要把 `reference_audios` 当作确定性音色控制手段**
- 它确实是 H3 官方支持的参数，值得在别的接法下再试（本轮试了两种都失败）
- 附带发现：`synthesize_speech` 支持 `pitch`（−12..12），
  是构造"明显不同的参考音色"最省事的手段

### 11.6 可用的客观测量方法

| 手段 | 结论 |
|---|---|
| 自相关 F0（干净场景） | ✅ 可用，且是唯一跨探针可靠的音色指标 |
| 谐波梳状滤波 | ❌ 八度错误，190Hz 判成 379Hz |
| 谱峰间距法 | ❌ 被共振峰包络带偏 |
| 目视频谱图（`showspectrumpic`） | ✅ **最终依据** |
| LTAS 形状距离 | ⚠️ 必须电平归一化，且**对信噪比敏感** —— 电平差 9dB 就能造出 12dB 的形状差，但音高没变。只能当辅助 |

### 11.6.1 三个已验证失败或不可靠的 DSP 估计器

用已知的干净 TTS 样本当标尺做过自检，三个里只有自相关过关：

| 估计器 | 失败原因 |
|---|---|
| 谐波梳状滤波（含/不含谱白化） | 八度错误；低 F0 偏置需按谐波数归一化，改完仍错 |
| 谱峰间距法 | 400 点窗只有 40Hz 分辨率；改 2048 点窗后仍被共振峰包络带偏 |
| 平均谱峰值取中位间距 | 同一段里谐波与共振峰混在一起，间距中位数不可解释 |

> **教训：任何新写的音高估计器，必须先用已知真值的干净样本自检，
> 再拿去测混音。顺序反了会得出漂亮但错误的结论。**

### 11.7 由此得出的生产规则

1. 每条含台词的镜头，提示词里的**音色描述词逐字复制**，不得改写
2. 生成后**人工逐条比对音色**，不统一就重生成该条（单条 $0.48，可接受）
3. 旁白/画外音（不需对口型）→ 走**独立 TTS**，音色 100% 固定
4. 绝不用后期变速/变调去凑音色统一
