# 性能：闸门、基线、归因

> **插件是嵌在别人的主应用里的。** 插件慢一点，用户就会说「DSH 卡了」。
> 功能做再好也救不回来——而且这类问题**不会报错**，它只会让人觉得 DSH 变慢了。
> 所以性能必须有**闸门**，不能靠感觉。

---

## P1 两道闸门

```bash
node scripts/perf.mjs                    # Host 端延迟与响应体
node scripts/render-probe.mjs            # 渲染开销（切换延迟 / CPU / 轮询）
node scripts/build.mjs --perf --render   # 两道都跑，作为构建的一部分
```

`--perf` / `--render` **要 DSH 正在跑**（前者要 web 端口，后者要 DSH Desktop 窗口），
所以默认**不跑**——构建不该依赖一个正在运行的服务。

**端口不是固定的 13144。** 13144 是独立 `dsh web` 的端口；DSH Desktop 跑的时候
宿主在另一个端口上（`netstat -ano` 找 DeepSeek Harness 那个进程）。探针连不上会报
「测不到」，而「测不到」不是「通过」——所以要 `--base` 指过去。

另有两条闸门随 `build.mjs` 自动跑：等价性回归（P8）与客户端 SSR 冒烟测试。

## P2 预算与实测基线

演示作品：72 镜 / 12 场。机器不同绝对值会变，**预算是不许越线的那一列**。

| 指标 | 预算 | 实测（2026-11-19，优化后） |
|---|---|---|
| 一轮刷新（面板实际用的 `/snapshot`）p95 | 60 ms | 12.8 ms |
| 端点 p95（最慢的 `snapshot` / `assets`） | 60 ms | 12.3 / 9.9 ms |
| 打开「生成」阶段（`/api/stage`）p95 | 400 ms | 23.9 ms |
| 打开工作台的切换延迟 | 1200 ms | 320 ms |
| 切走工作台 | — | 503 ms |
| 工作台净 CPU 开销（A/B 对照） | 20 % | −1.6 %（比会话还省） |
| 面板藏起来后的轮询次数（8 秒） | 0 次 | 0 次 |
| 冷启动（插件刚装完那一次） | — | 14–330 ms，**不计入判定** |

> 切换延迟的预算**不是拍的**：同一台机器上，用户自己的「自媒体工作台」插件打开
> 耗时 244–1136 ms。预算定在 1200 ms =「不许比参照插件更差」。**换机器要重新测参照插件。**
>
> `/snapshot` 的响应体随作品规模增长（72 镜 ≈ 37 KB，每 4 秒一次 ≈ 9 KB/s）。
> **作品的镜头数再上一个量级时，要重新量这一条。**

## P3 六条规矩（每条都对应一个已修掉的坑）

1. **一次刷新只发一个请求。** `/drama-desk/api/snapshot` 一次给全（顶栏 + 网格 +
   阶段条 + 设置）。四个端点就是四倍 HTTP 开销。
2. **数据没变就不重渲染。** Host 给每个视图一个 `revision`（文件 mtime + size）；
   客户端比对后**跳过 setState**。否则每几秒就把几十个格子销毁重建一次。
3. **面板不可见就停轮询。** 宿主可能把面板留在 DOM 里只是不显示——组件不卸载，
   轮询也不会停。用 `IntersectionObserver` 判可见性，藏起来立刻停，重新可见时补一次。
4. **不要用 `filter: blur()` 做全屏氛围层。** 三个 `56vmax` 的模糊光斑让渲染进程
   常驻一个核以上（实测 110 % CPU）。改成直接画径向渐变——视觉几乎一样，只是一次
   光栅化，没有逐帧开销。
5. **不要在同一元素上同时用渐变背景与 `backdrop-filter`。** 见 `rendering.md` R3。
6. **Host 端的重活要缓存。** 磁盘余量、资产体积这类「慢慢才变」的数，用几秒的 TTL
   缓存；每轮轮询都去 `statfs` 一遍是白费力气。

## P4 测的时候要小心

- **CPU 必须 A/B 对照。** DSH 的会话界面本身就在忙（流式输出、动画），单看一个数
  没有意义——**差值**才是插件的开销。
- **第一轮是冷的，要单独量。** 插件刚装完 / DSH 刚重启时缓存是空的：体检器要起子进程、
  磁盘要 `statfs`、抽帧要跑 ffmpeg。实测 `snapshot` 冷启动曾到 276 ms，而热态只要 16 ms。
  冷启动不是轮询开销（它发生在面板挂载那一刻），把它算进 p95 只会让闸门随机失败。
  所以 `perf.mjs` 每端点先打一发热身、**单列「冷启动」列、不计入判定**。
- **切换延迟要用「另一个主面板」来量**，不要点侧栏入口当开关（点它总是**选中**这个
  面板，不会收起）。
- **判「面板可见」看几何**（宽高非零），不看「元素还在不在」。
- **PS 5.1 把没有 BOM 的 `.ps1` 当 ANSI 读**，探针脚本里有中文字面量就必须带 UTF-8 BOM，
  见 `windows.md` W4。

## P5 探针自己的失败模式

探针也会骗人。它曾把「等一个永远不会出现的标志元素」当成 6 秒延迟，把「点击了工作区
标题而不是会话行」当成面板没隐藏。**所以探针的每个判据都要能用截图或 DOM 查询独立
验证**——探针报「超预算」时，先怀疑探针。

更严重的一种：**探针测不到，却报「通过」。** 标志元素的文案一改，探针就找不到面板，
于是延迟测成 `-1`、CPU 测成 `0`——而 `-1 > 1200` 为假，于是「通过」。那是把「没测」
说成「没问题」。

已落到代码里的对策：

1. 标志元素用**插件独占**的一行字（`AI 短剧生产线`），不要用输入框的 placeholder
   ——改一次文案探针就瞎了；
2. 探针**测不到就失败**：`switchAvg < 0` / `hiddenPolls < 0` 一律计入问题。

窗口要按**进程名**认（`DeepSeek Harness.exe`），不要按标题认：浏览器里开着的 DSH
网页版窗口标题也叫「DeepSeek Harness」，否则「截桌面应用」会截成网页。

## P6 先分清「谁的慢」

同一个 `DramaDeskService`，同一份作品，两种服务器：

| 端点 | 独立 Node 服务器 | DSH Host 里 | 倍数 |
|---|---|---|---|
| `/snapshot` | 12.0 ms | 66.3 ms | 5.5× |
| `/pipeline` | 11.7 ms | 73.0 ms | 6.2× |
| `/assets` | 14.1 ms | 82.0 ms | 5.8× |

**我们的代码只值 12 ms**，剩下的六倍是宿主环境给的。验证方式：`node scripts/profile.mjs`
把同一个 service 挂在普通 `http.createServer` 上，用同样的作品、同样的请求量量一遍。

> 所以「优化插件」这条路的天花板是 12 ms → 0 ms，而 66 ms → 12 ms 那一段**不在
> 插件手里**。

### 宿主进程会自己在空转

DSH 的 Host 进程长时间运行后，可能在**完全空闲**时烧掉两三个核（实测一个线程 98.8%，
进程总计 254 %），而 10 秒内只有 167 次文件读——那是**纯 CPU 自旋**，不是 I/O。

排查时逐一证伪过：禁用本插件（253.7 %，不是它）、逐个禁用其它插件（始终 253–263 %）、
内存泄漏（工作集稳定）、磁盘 IO（读次数很低），最后**重启 DSH** → 254 % → 2.7 %。

> **结论：这是宿主长时间运行后的缺陷，不是插件的。**
> **量之前先确认宿主没有空转**，否则量到的是宿主的问题——12 ms 的代码能给你量出 66 ms。

## P7 但插件自己的账也要算清

| 位置 | 原来 | 改成 | 现在 |
|---|---|---|---|
| `assets()` 逐个探测 101 个文件是否存在 | 10.6 ms 串行 | 有上限的并发池（`fsx.js` 的 `mapLimit`，上限 32） | ~2.5 ms |
| `pipeline()` 逐镜探测 72 份验收报告 | 6.8 ms（69 次失败探测） | 一次 `readdir` 拿全，只读真存在的 | ~0.3 ms |
| 生成台每开一次就起一个 Python 子进程 | 268 ms | 按**真源的指纹**缓存（`scenes.json` + `shots.json` 的 mtime+size） | 0.3 ms |
| 72 镜的提示词产物逐镜读 | 33.8 ms（144 次探测） | 两个目录各列一次，并行读 | ~2 ms |
| 72 镜的封面来源逐镜找 | 35.8 ms（360 次探测） | 三个目录各列一次 | ~1 ms |
| 一轮快照里 `listWorkspaces()` 被问四次 | 4×2.2 ms | 一秒 TTL 的清单缓存 | 一次 |

一轮刷新：66 ms → 12.8 ms；生成阶段视图：362 ms → 16 ms。

> **两处「逐个问」改「一次列目录」的通用道理：**「这个文件在不在」用 `stat` 回答一次；
> 「这一堆文件里有哪些」用一次 `readdir` 回答全部。**失败探测也是往返**——目录里没有
> 文件时，你为「不在」这个事实付了一次往返的价钱。

## P8 缓存的纪律：缓存**清单**，不缓存**某一镜的判定**

`check()` 原本要跑编译器。给它加缓存时，第一版把整个答案存了下来——而答案里的
`stale` / `changed` 是**某一镜**的判定。于是先问 A 镜、再问 B 镜时，**B 镜拿到的是
A 镜的答案**。界面照样渲染，只是内容是假的——**静默的错误比慢更糟**。

> **规则：一个缓存项里如果混着「与请求无关的部分」和「与请求相关的部分」，
> 就只能缓存前者。** 这里缓存的是「哪些镜过期了」这份清单，单镜的判定由清单现算。
>
> 而且必须**证明**两种口径等价：编译器带 `--shot X` 与不带 `--shot` 对 X 这一镜的
> 判定一致（`tests/equivalence.mjs` 第 3b 项）。

**等价性要有闸门**：

```bash
node tests/equivalence.mjs
```

**优化过的答案必须与优化前逐字节相同。** 优化改的是「怎么问」，不是「答什么」。
`scripts/build.mjs` 会跑它——没有演示作品时它自己跳过（不是假装通过）。

## P9 闸门只量你量过的东西

`perf.mjs` 早期只量被轮询的端点，**打开一个阶段**走的 `/api/stage` 不在里面——于是它
350 毫秒的成本（其中 268 毫秒是每次都起一个 Python 子进程）从来没被量过。现在它在表里，
预算 400 ms（点开的路径，慢一点没关系，但不能慢到让人等）。

**加一条新路径时，记得给它也加一道闸门。**
